# Google Sheets連携セットアップ

## 構成

GitHub Pagesには静的な `index.html` だけを配置します。スプレッドシートIDと接続キーはフロントのソースへ書かず、Apps ScriptのScript Propertiesに保存します。

データは次の6シートに分けて保存されます。

- `Projects`: 案件情報、参加者名、スプリット、タスク状態
- `ProductionLogs`: ギター録音・楽器トラック・サンプルの明細
- `DeletedProjects`: 消去した案件の全情報と消去日時
- `DeletedProductionLogs`: 消去した案件に紐づく全制作ログ、案件名、消去日時
- BetaAnalyses: 音楽的貢献度分析v3の下書き・確認済み結果
- DeletedBetaAnalyses: 消去した案件のベータ分析履歴

## セットアップ

1. Googleスプレッドシートを新規作成し、URL内のスプレッドシートIDを控えます。
2. Apps Scriptプロジェクトを作成し、`Code.gs` と `appsscript.json` の内容をコピーします。
3. Apps Scriptの「プロジェクトの設定」→「スクリプト プロパティ」に次を追加します。
   - `SHEET_ID`: 手順1のスプレッドシートID
   - `API_KEY`: 十分に長いランダムな接続キー
4. エディタから `setupDatabase()` を1回実行し、権限を承認します。
5. 「デプロイ」→「新しいデプロイ」→「ウェブアプリ」を選び、「実行ユーザー: 自分」「アクセスできるユーザー: 全員」に設定します。API_KEYによる認証はCode.gs側で行われます。
6. 発行された /exec で終わるWeb App URLをSPLITLABの「自動同期」で入力します。接続キーも入力します。ローカル版とGitHub Pagesは保存領域が別なので、公開ページでは初回のみ再入力が必要です。

Web App URLはブラウザのlocalStorage、接続キーはタブを閉じると消えるsessionStorageにのみ保持され、リポジトリには保存されません。

## セキュリティ上の重要事項

GitHub Pagesは静的配信なので、HTMLやJavaScriptへ埋め込んだ秘密値を隠すことはできません。この構成では機密値をApps Script側へ置き、接続キーを実行時に入力します。ただし、接続キーは認証済み利用者自身のブラウザ開発者ツールからは確認できます。

不特定多数へ公開する場合や利用者ごとの権限制御が必要な場合は、接続キー方式ではなくGoogle OAuth / Identity Platform、またはCloudflare Worker等の認証付きバックエンドを追加してください。
## Gemini APIの無料枠について

Gemini APIには対象モデルの無料枠がありますが、利用可能地域、対象モデル、レート上限はGoogle側で変更される場合があります。無料枠を超えた場合や対象外地域ではエラーになり、SPLITLABはローカル基準値へフォールバックします。分析対象の制作ログはGemini APIへ送信されるため、無料枠ではGoogleのサービス改善に利用される可能性がある点も確認してください。
## 文章から制作ログを作成

案件詳細の「文章からログを作成」へ作業報告を入力すると、Geminiが担当者・カテゴリ・本数・貢献範囲・制作負荷（カロリー）・関わり方・役割へ分解します。候補は登録前に選択・修正できます。関わり方（contributionMode）は原文から明確に判断できる場合だけ設定され、判断できない場合は未選択のままになります。

## 5軸貢献分析（metricVersion 5）

最終レコメンドは次の5軸の加重平均です。ウェイトは `Code.gs` と `app.js` の `ANALYSIS_WEIGHTS` に定数化されています。

| 軸 | ウェイト | 算出 |
| --- | --- | --- |
| Quantity / 物量 | 25% | ローカル機械計算（本数・貢献範囲・制作負荷）。AI判断なし |
| Musical Weight / 音楽的比重 | 30% | Gemini（`analyzeProject_`） |
| Creative Agency / 創作主体性 | 20% | Gemini（同じ1回の呼び出し） |
| Creative Resolution / 完成・収束寄与 | 20% | Gemini（同じ1回の呼び出し） |
| 5-Axis Musical / 5軸音楽分析 | 5% | Gemini（`analyzeBeta_`） |

confidenceが0.70未満のAI軸、および5軸分析内のconfidence 0.70未満のelement・contributorは計算から除外されます。除外により材料が足りなくなった軸は「判定保留」となり、50:50を作らずウェイトから外して残りの軸を100%へ再正規化します（`combineAxes_`）。

## 接続の切り替え（ワークスペース）

案件データはスプレッドシート単位で完全に分離されます。アプリはヘッダーの切り替えメニューで接続先を選び、localStorageの保存キーへワークスペースIDの接尾辞を付けることで、別シートの案件が混ざったり、未同期の案件が別シートへ送信されたりしないようにしています。

- 接続の一覧（ラベルとURL）は**そのブラウザのlocalStorageにだけ**保存され、スプレッドシートへは同期されません
- 接続キーは従来どおりsessionStorage（タブを閉じると消える）に、ワークスペースごとに保持されます
- 既存ユーザーの単一接続は「メイン」ワークスペースとして扱われ、保存キーは旧キーのままです（データ移動なし）
- 一覧からの削除はその接続のローカルデータのみを消去し、スプレッドシートには影響しません

## 参加者名

参加者は案件ごとに名前を設定できます（案件情報モーダルの「参加者 1 / 参加者 2」）。内部キーは `A` / `B` のままで、表示名だけを `Projects` シート末尾の `participantsJson` 列へ保存します。未設定の過去案件は従来どおり tada / riku として読み込まれます。

AIプロンプトへは案件の参加者名が渡され、返ってきた担当者名は `personKey_` で内部キーへ戻されます。分析結果のキーも `betaPercentA` のようにA/B基準へ統一済みです（`metricVersion: 6`）。人数を3人以上へ増やす場合は、`PERSON_KEYS` を起点に splitA/splitB とスライダーUIの2択構造を置き換える必要があります。

`ProductionLogs` シートの末尾には `contributionMode` 列が、`Projects` シートの末尾には `participantsJson` 列が追加されています。既存シートは `setupDatabase()` を再実行するか、通常の同期時にヘッダーが自動更新されます。列が空の過去ログはそのまま読み込め、修正は不要です。

この機能を追加した後は、Apps Scriptの `Code.gs` を更新し、ウェブアプリを新しいバージョンとして再デプロイしてください。入力した文章は分析のためGemini APIへ送信されます。
## 自動同期と担当者名

画面上の担当者名は `tada` / `riku` です。内部データでは既存互換のためA/Bを使用しますが、新しくGoogle Sheetsへ保存する制作ログは担当者列に `tada` / `riku` と記録されます。

一度「自動同期」から接続設定を行うと、初回だけ全案件を取得し、進捗率と残りの目安を画面上部へ表示します。以降は変更した案件だけを送信し、前回同期以降に他端末で更新された案件だけを取得します。バックグラウンド同期ではボタン表示や画面の再描画を行わず、変更が届いた時だけ一覧を更新します。変更停止から約0.5秒後、画面を開いている間は10秒ごと、タブへ戻った時にも差分を確認します。接続キーはsessionStorageに保存されるため、タブを閉じた後は安全のため再入力が必要です。
## 制作ログの5段階評価

貢献範囲は「1: ワンポイント（単発の差し込み・装飾）」「2: 1セクション（Aメロ・サビなど一部の構成）」「3: 複数セクション（2〜3程度の構成にまたがる範囲）」「4: 曲の大部分（サビ以外にも複数箇所で使われる、曲の骨格に近い要素）」「5: 曲全体（一曲を通して存在する要素）」です。

制作負荷（カロリー）は「1: 軽作業」「2: やや工夫が必要」「3: 標準的な負荷」「4: 高負荷」「5: 非常に高負荷」です。難易度、専門性、試行錯誤、所要労力をまとめて評価します。

旧バージョンの秒数・編集数ログはブラウザ側で自動換算されます。既存のスプレッドシートを使う場合は、更新した Code.gs を再デプロイ後に setupDatabase() をもう一度実行してください。ProductionLogs の末尾へ scope と effort 列が追加され、既存列や既存データは移動しません。
## 案件アーカイブ

ダッシュボードの案件カードから完了案件をアーカイブできます。アーカイブするとステータスは「完了」になり、通常一覧から「完了した案件」へ移動します。アーカイブ一覧からいつでも復元できます。

アーカイブ状態は Projects シート末尾の archived と archivedAt に保存されます。この更新を導入する場合も、Code.gs を反映して setupDatabase() を実行し、ウェブアプリを新しいバージョンとして再デプロイしてください。

アーカイブ済み案件には小さな「消去」ボタンが表示されます。消去にはScript Propertiesと同じ `API_KEY` の再入力が必要です。消去前に案件は `DeletedProjects`、制作ログは `DeletedProductionLogs` へコピーされ、通常のシートから取り除かれます。削除履歴は同期時の復活防止にも使われるため、履歴シートの行は削除しないでください。

## 制作ログ分析と5軸音楽分析の統合

以前は「音楽分析 β」という別画面で5軸音楽分析(v3)を個別に実行していましたが、現在はメイン画面の「Google AIで分析」に統合されています。1回のクリックで、物量・音楽的比重(v2)の分析と5軸音楽分析(v3)の両方を実行し(`analyzeCombined`アクション)、最終レコメンドは**物量42.5% + 音楽的比重(v2のGemini判定)42.5% + 5軸音楽分析(v3)15%の加重平均**です。5軸音楽分析の重みは15%に抑え、残り85%を物量と音楽的比重に均等配分しています。5軸音楽分析の結果は記録として自動的に `BetaAnalyses` へ下書き保存されます(閲覧・編集用の専用画面はありません)。

導入時は最新の `Code.gs` を反映し、`setupDatabase()` を再実行して `BetaAnalyses` / `DeletedBetaAnalyses` の2シートを作成した後、既存ウェブアプリを新しいバージョンとして再デプロイしてください。案件を消去すると5軸音楽分析の記録は `DeletedBetaAnalyses` へ移されます。
